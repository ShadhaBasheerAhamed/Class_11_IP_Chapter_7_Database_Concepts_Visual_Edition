7.1 Introduction

Schools maintain information about students, attendance and guardians. A class teacher may mark P for Present and A for Absent every working day.

Roll No.StudentAttendance dateStatus
01Aarav01-09-2026P
02Diya01-09-2026A
01Aarav02-09-2026P

For 50 students and 26 working days, the teacher may have to maintain 50 × 26 = 1,300 attendance entries in a month. As data grows, manual record keeping becomes tedious.

Problems with manual registers

  • Re-entering student details when promoted to the next class.
  • Inconsistent spelling or skipped student records.
  • Loss or damage of the register.
  • Calculation errors while preparing attendance totals.

Why computerised records?

  • Copy student details into a new class file.
  • Search student or guardian information.
  • Add details when a new student joins.
  • Modify student or guardian details.
  • Delete records when a student leaves.
Remember: Computerised files make storing and changing data easier, but a traditional file system still has limitations. DBMS helps overcome them.

7.2 File System

Definition: A file is a container used to store data in a computer. Files are stored on a computer's storage device.

File contents may include text, program code, CSV (comma-separated values), pictures, audio/video and web pages.

7.2.1 Limitations of a File System

Learn these six headings. In exams, write the meaning and one suitable example for each.

1. Difficulty in Access

Files do not provide a built-in mechanism to retrieve data. Application programs must be written. Unexpected search requirements can be difficult to handle.

Example: Finding all students absent on a particular date needs a program.

2. Data Redundancy

The same data is duplicated in different files. This wastes storage.

Example: Student name and guardian details appear in both STUDENT and ATTENDANCE files.

3. Data Inconsistency

Same data stored in different places does not match after an incomplete update.

Example: A student's name is corrected in STUDENT but not in ATTENDANCE.

4. Data Isolation

Related data is kept in separate files without proper links. Different formats make combined retrieval difficult.

Example: Student details and attendance are maintained separately.

5. Data Dependence

Programs depend on the file's structure or format. If the structure changes, all programs using it may need changes.

Example: Adding a field to a file may require modifying existing programs.

6. Controlled Data Sharing

It is difficult to provide different access permissions to different users.

Example: Parents may view attendance, but only teachers should update it.

Memory trick: D-D-D-D-D-C → Difficulty, Data Redundancy, Data Inconsistency, Data Isolation, Data Dependence, Controlled Data Sharing.

7.3 Database Management System (DBMS)

Definition: A DBMS is software used to create and manage databases. It allows users or application programs to store, retrieve, update, modify and delete data.

A database is an organised collection of logically related data. DBMS acts as an interface between the database and users/application programs.

File System → DBMS: what changes?

  • Related data is organised into linked tables.
  • Repeated student names need not be stored in every table.
  • A unique Guardian ID (GUID) identifies a guardian.
  • RollNumber links attendance to a student.

Costs / limitations of DBMS

  • Increased complexity to maintain security, consistency, sharing and integrity.
  • Increased data vulnerability because data is stored centrally; hardware/software failure may affect many users.
  • High setup and maintenance cost: hardware/software, user training, backups and recovery.

Database terms in 7.3

Database Schema

The design or logical structure of a database. It describes tables, attributes, data types, constraints and relationships.

Data Constraint

A restriction on the type or values of data allowed in a column. Example: RollNumber must be unique and not NULL.

Metadata / Data Dictionary

Data about data. DBMS stores schema and constraints in a database catalog/data dictionary.

Database Instance

The actual data or snapshot of the database at a particular time. It changes when data is inserted, updated or deleted.

Query

A request to a database to obtain information in a desired way. Example: Find students present on a given date.

Data Manipulation

Three operations: INSERT (add), DELETE (remove), UPDATE (modify) records.

Database Engine

The underlying component/programs used by a DBMS to create databases and handle queries and data operations.

7.4 Relational Data Model

A data model describes how data is defined, represented, related and constrained. The most commonly used model is the Relational Data Model.

Other models mentioned in the textbook: object-oriented, entity-relationship, document and hierarchical data models.

Relational model: Data is stored in tables called relations. Tables are connected through common attributes/fields.

School database: three related relations

GUARDIAN

GUID · GName · GPhone · GAddress

STUDENT

RollNumber · SName · SDateofBirth · GUID

ATTENDANCE

AttendanceDate · RollNumber · AttendanceStatus

STUDENT.GUID connects a student to GUARDIAN.GUID. ATTENDANCE.RollNumber connects an attendance record to STUDENT.RollNumber.

7.4.1 Three Important Properties of a Relation

Property 1 – Attributes / columns

  • Each attribute in a relation has a unique name.
  • Sequence/order of attributes is immaterial.

Property 2 – Tuples / rows

  • Each tuple is distinct; no two rows should be identical in all attributes.
  • Sequence/order of tuples is immaterial.

Property 3 – Values in a relation

  • Values in one attribute must belong to the same domain/data type.
  • Each value must be atomic (indivisible into meaningful subparts).
  • An attribute cannot store multiple values in one cell.
  • NULL represents an unknown or non-applicable value.

7.5 Keys in a Relational Database

Keys help uniquely identify records and establish relationships between tables.

A relation must have a way to distinguish each tuple. A key uses one or more attributes for this purpose.

1. Candidate Key

One or more attributes that can uniquely identify every tuple. Each candidate key is a possible choice for the primary key.

Example: In GUARDIAN, GUID and GPhone are both unique, so both can be candidate keys.

2. Primary Key

The candidate key selected by the database designer to uniquely identify tuples. It must be unique and cannot be NULL.

Example: If GUID is selected, GUID is the primary key and GPhone becomes an alternate key.

3. Alternate Key

Candidate key(s) not selected as the primary key.

4. Composite Primary Key

A primary key made of two or more attributes when no single attribute can uniquely identify a record.

Example: In ATTENDANCE, RollNumber repeats on different dates and AttendanceDate repeats for different students. Together, (AttendanceDate, RollNumber) uniquely identifies one attendance entry.

5. Foreign Key

An attribute in one (referencing) relation that refers to the primary key of another (referenced) relation. It creates a relationship between tables. A foreign key may be NULL if it is not part of the primary key.

These are concise, exam-ready answers based on the readable exercise pages you shared. The photographed pages clearly show Q1, Q2 and Q8–Q13; one intervening exercise page is blurred, so I have not invented its question text.

1. Give the terms

  1. Collection of logically related records – Database.
  2. DBMS creates a file containing description about data stored in the database – Data dictionary / Database catalog (metadata).
  3. Attribute that uniquely identifies tuples – Key (more specifically, a candidate key).
  4. Special value stored when actual data is unknown – NULL.
  5. Unique identifying attribute not defined as primary key – Alternate key.
  6. Software used to create, manipulate and maintain a relational database – DBMS / RDBMS.

2. Why can a foreign key have NULL? Give an example.

A foreign key may be NULL when a relationship is not yet known or is not applicable, provided that the foreign-key column is not part of the primary key. Example: a student record may temporarily have no guardian ID recorded.

8. School canteen database – answer framework

  • Use an ITEM relation such as ITEM(ItemID, ItemName, Price, Calories). ItemID is the primary key; ItemName can be UNIQUE if item names must not repeat; Price should be greater than zero.
  • Use a BILL relation such as BILL(BillNo, BillDate, StudentID) and BILL_ITEM(BillNo, ItemID, Quantity). BillNo identifies a bill; (BillNo, ItemID) can be a composite primary key in BILL_ITEM. BillNo and ItemID are foreign keys.
  • Store Calories with ITEM because it describes the item, not an individual purchase.

9. EMPLOYEE–DEPENDENT database

EMPLOYEE(AadharNumber, Name, Address, Department, EmployeeID): likely candidate keys are AadharNumber and EmployeeID if both are unique. DEPENDENT(EmployeeID, DependentName, Relationship): EmployeeID refers to EMPLOYEE. The degree of EMPLOYEE is 5; the degree of DEPENDENT is 3.

10. School uniform database – insertion checks

  • UNIFORM(UCode, UName, UColor): UCode is primary key; UName is NOT NULL.
  • (7, Handkerchief, NULL): allowed if UCode is new and UName is supplied; UColor may be NULL because no NOT NULL constraint is shown.
  • (4, Ribbon, Red): rejected because UCode 4 already exists (primary key duplicate).
  • (NULL, 8, White): rejected because primary key UCode cannot be NULL (and the tuple's values do not match the stated three-column structure).
  • COST(UCode, Size, Price): composite primary key (UCode, Size); Price > 0. Duplicate combinations are rejected; price must be positive.

11. Multiplex MOVIE and AUDI

MOVIE_ID can be the primary key of MOVIE if each movie has one unique ID. AUDI should use a composite primary key such as (Movie_ID, AudiNo), because one movie can be shown in more than one auditorium and an auditorium can screen different movies. AUDI.Movie_ID is a foreign key referencing MOVIE.Movie_ID.

12. STUDENT–PROJECT database

  • Primary keys: STUDENT – RollNo; PROJECT – ProjectNo; PROJECT_ASSIGNED – Registration_ID (or the composite key if the design permits multiple assignments per registration).
  • Foreign keys in PROJECT_ASSIGNED: Registration_ID references STUDENT.Registration_ID; ProjectNo references PROJECT.ProjectNo.
  • Registration_ID in STUDENT appears unique in the shown data, so it can be an alternate key.
  • Duplicate RollNo cannot be assigned because RollNo is the primary key.

13. Can these records be inserted?

  • Student record with missing RollNo – No, primary key cannot be NULL.
  • Student record with missing Registration_ID – Yes only if Registration_ID is not defined as NOT NULL / primary key / required foreign key; the shown table alone does not establish a NOT NULL constraint.
  • Project detail without SubmissionDate – Yes only if SubmissionDate allows NULL or has a default value.
  • PROJECT_ASSIGNED record with Registration_ID IP-101-19 and ProjectNo 206 – No if either referenced value does not exist in the parent tables; foreign-key values must match existing referenced keys.
